# Native database accounts

This provider authenticates a username and password directly against a server-owned credential
store. Keycloak and JWT issuance are not required. The provider was introduced in preview.14.
The bounded password-admission queue described below requires the preview.15 candidate or later.
Use matching client and host package versions; see [candidate status](preview15-validation.md).
Existing JWT/certificate configurations and unauthenticated embedded repositories retain their
behavior. Changing an existing deployment to native accounts is explicit, not an automatic migration.
See the [validation record](native-account-validation-20261029.md) for Windows/Linux results and scope.

## Configuration and account creation

Start with [hostsettings.password.example.json](../samples/InterfaceDB.TcpStore.Host/hostsettings.password.example.json).
Use the normal TLS certificate, compatibility manifest and persistent application directory from
the [host guide](tcp-transport.md). Select `authenticationMode: "Provider"` on both ends.
The sample configures these native-account settings under `localAccounts`:

| Setting | Meaning |
| --- | --- |
| `accounts.authority` | Stable deployment identity beginning `idb-local:`. Keep it unchanged across restarts. |
| `accounts.accountMode` | `SingleAccount` allows exactly one account; `MultipleAccounts` allows several, up to the configured limit. Changing to single mode fails if more than one account exists. |
| `accounts.creationMode` | `Administrators` (default), `Everyone` (anonymous registration), or `Disabled` (no remote account creation). |
| `accounts.creatorAccountIds`, `creatorRoles` | Allowlisted stable account IDs or roles permitted to create accounts in administrator mode. Defaults: no IDs and role `account-admin`. |
| `accounts.newAccountRoles` | Server-assigned roles for new registrations; default `database-user`. They cannot include a configured creator role. |
| `storageDirectory` | Dedicated credential store, separate from application data. Never expose this store as a TCP alias. |
| `storageProvider`, `encryptionMethod` | The sample supports `SegmentCore` and `AesGcm`. The host API supports injected implementations. |
| `encryptionKeyEnvironmentVariable` | Name of a variable containing a base64-encoded random 32-byte key, supplied from deployment secrets. JSON contains the variable name only. |
| `passwordHashingMethod`, `passwordHashIterations` | Sample uses `Pbkdf2Sha256`, default 600,000 iterations; accepted range 600,000–2,000,000. |
| `bootstrapUsername`, `bootstrapPasswordEnvironmentVariable` | Provision the first administrator before the sample starts listening. Bootstrap only succeeds on an empty credential store. |

Passwords require at least 12 characters and at most 1,024 UTF-8 bytes. Usernames are 1–128 ASCII
letters, digits, `.`, `-`, `_` or `@`, normalized to lowercase. A random stable account ID is
generated by the server; neither the username nor password is the data-partition identifier.

Provision the encryption key and bootstrap password through the deployment's secret manager or
process environment. Keep the encryption key outside the credential directory and retain it with
protected backups. A missing key, an unsupported encryption method, a wrong key, or an existing
catalogue with a different authority prevents startup. There is no plaintext fallback.
Changing the bootstrap password environment variable after provisioning does **not** reset an
existing account. Remove the bootstrap secret after the first successful provisioning.

With the sample, an empty store without bootstrap configuration cannot start. In a custom host,
call `ProvisionFirstAccountAsync` locally before listening. No network request can invoke bootstrap
or elect itself administrator. `Everyone` is an explicit self-registration choice; it never allows
the caller to supply roles, claims, an account ID, or someone else's partition.

## Data separation

Authentication establishes an identity; [data access policies](data-access-policies.md) select the
data it may access. Native identities contain trusted `iss` (authority), `sub` (stable account ID),
roles and server-assigned membership claims, just as policies need from a validated JWT identity.
These are claims on a server-created principal, not a JWT sent by the client.

For **MultipleAccounts**, every store needs an explicit partitioning `IDataAccessPolicy`.
An omitted/unrestricted policy fails host startup. A custom policy returning an unrestricted
scope is denied at runtime. The sample's `dataAccessPolicy: "subject"` gives each account its
own data. An administrator's ability to create accounts does not grant access to those accounts'
data. All existing key, page, batch, ownership, change-feed and subscription boundaries still apply.

For shared families/tenants, an administrator can assign a `groups` or `tenant_id` claim through
the trusted management API and use `ClaimDataAccessPolicy` or a contract policy. The sample
supports `dataAccessPolicy: "claim"` plus `dataScopeClaim`. Membership is assigned by the server;
`RequestedScope` only selects an already-authorized membership. Self-registration assigns no
membership claims, so a claim-isolated account requires administrative provisioning before access.

For **SingleAccount**, an explicit partition policy is optional. `dataAccessPolicy: "none"`
uses the existing shared/unpartitioned data scope after login. Choose the policy before writing
data: changing authority, account identity, or policy does not move existing data into a new scope.

## Client login and registration

Start with your normal `TcpStoreClientOptions`, including endpoint, alias, manifest and certificate
trust. Do not disable server certificate validation. Credentials are requested only after TLS has
authenticated the server:

```csharp
using Idb.Authentication;
using Idb.Transport;

var credentials = new UsernamePasswordCredentialsProvider("alice", cancellationToken =>
    secretStore.ReadPasswordAsync("interfacedb/alice", cancellationToken));
var connection = existingConnectionOptions with
{
    AuthenticationMode = TcpStoreAuthenticationMode.Provider,
    TokenProvider = null,
    CredentialsProvider = credentials
};
await using var database = await TcpEncodedEnvelopeStore.ConnectAsync(connection);
```

`secretStore` is your application's secret abstraction. Its method returns `ValueTask<string>`.
The same connection options work with `TcpRepository<TContract>`; contract configuration and
serializer registration are unchanged. A repository pins its first server-authenticated account
and data scope. Switching accounts requires a new repository, even if both accounts share a group.
Passwords are not persisted in cache identities or scope receipts. Native cache identity discovery
requires an online authentication; it cannot verify a new password/account from an offline cache.

Administrator-created registration supplies the creator's credentials explicitly:

```csharp
AccountIdentity account = await TcpAccountClient.CreateAsync(
    connection, "new-user", newPassword, administratorCredentials, cancellationToken);
```

For `Everyone`, omit `administratorCredentials`. Registration returns only the new stable account
identity, not credentials or a logged-in session. The new user must log in. A duplicate/limit
rejection is generic. A lost acknowledgement or uncertain credential commit is reported as
`OutcomeUnknown`; do not automatically retry or assume creation failed. Reconcile with the
trusted administrator or attempt login using the submitted credentials.

## DI and storage abstractions

The host depends on `IAuthenticationProvider`. Existing JWT validation is adapted by
`JwtAuthenticationProvider`; native authentication is `LocalAccountAuthenticationProvider`.
The native provider receives `IDatabaseAccountStore`, `IPasswordHasher` and
`IAccountCreationPolicy`. Account registration uses `IDatabaseAccountManager`; clients supply
`IClientCredentialsProvider`. Custom providers/strategies can be registered without changing TCP
or the data policy implementation.

`EncryptedDatabaseAccountStore.OpenAsync` composes any exclusively owned durable
`IEncodedEnvelopeStore` with an `IContextualEncryptor`. The sample uses SegmentCore plus the
existing AES-GCM implementation. The adapter authenticates its authority/storage context and
checks encryption at startup; it rejects no-op and context-insensitive implementations. Custom
cryptography still requires independent review: this self-check is not proof of cryptographic strength.

Register the opened account store and call `services.AddLocalAccountAuthentication(options)`.
Custom `IPasswordHasher` and `IAccountCreationPolicy` implementations can be registered first.
Resolve `IAuthenticationProvider` and `IDatabaseAccountManager` into the corresponding
`TcpStoreHostOptions` properties. Also configure `AuthorizeIdentity` for alias/operation admission
and the appropriate `IDataAccessPolicy` for each store. Dispose the host before its dependencies;
the composition root owns the backing store and encryptor lifetimes.

Password hashes use a fresh 16-byte salt, PBKDF2-SHA256 and constant-time hash comparison. The
catalogue contains hashes, not reversible passwords; AES-GCM protects those hashes and account
metadata at rest. The two protections serve different purposes. No password recovery endpoint
exists. The default uses platform cryptography without adding a hashing-library dependency;
`IPasswordHasher` permits another reviewed algorithm. See [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Management, session validity and operating limits

The native provider's trusted local service API includes `CreateManagedAccountAsync` (roles and
claims), `ChangePasswordAsync` (current password required), and `SetDisabledAsync` (administrator
required). Only ordinary account creation is exposed as a new TCP management operation. There
is no remote role-edit, password-reset, account-delete or MFA API in this change. Use a trusted
administration service or an external identity provider if those workflows are needed.

Password changes preserve the account ID and increment its security version. Disabling an account
also increments the version. Existing sessions are checked against current account state before
operations and notifications; an expired, disabled or changed credential version is denied.
The in-memory session lasts five minutes by default, configurable from one second to ten minutes,
and remains bounded by the host's maximum session lifetime. Reconnect authenticates again.
This does not retract data already downloaded or cancel an operation already admitted.

Defaults are 10,000 accounts, two concurrent password computations, and **60 password-work
admissions per minute across this provider instance**. The rate budget includes successful logins,
registration and password changes. By default, up to 32 requests may wait for a password worker,
for at most two seconds. Tune `MaximumQueuedPasswordChecks` (0–1,024) and
`PasswordAdmissionTimeout` (zero–30 seconds), alongside `AttemptsPerMinute` (1–10,000),
`MaximumConcurrentPasswordChecks` (1–32) and host connection limits. Queue saturation, an admission
deadline or an exhausted work budget raises `AuthenticationBusyException`, reported over TCP as
`Busy`; it is not an invalid-password result or an uncertain account mutation. Cancelled or rejected
waiters do not consume the password-work rate budget. An exposed login endpoint also needs deployment-level abuse
controls: a global budget alone cannot prevent an attacker exhausting that budget.

Password hashing is deliberately expensive. A persistent encoded-store connection authenticates
once; it does not rehash a password per record. The typed TCP repository opens short connections
per operation, and native mode therefore pays for password verification on each connection,
including discovery/subscription connections. This feature has correctness tests, not a throughput
claim or a comparison with JWT performance. Measure the intended workload before choosing limits.

The bundled credential adapter keeps a bounded catalogue in memory and atomically rewrites the
encrypted catalogue on account changes. The default encoded bound is 16 MiB, with a 100,000-account
hard ceiling; the actual capacity depends on grants and hashes. Account management is not intended
as a high-volume storage workload. A larger installation can inject another durable account store.
Uniqueness, single-account limits and optimistic security-version updates must remain atomic.
A write with an uncertain outcome faults the credential adapter until controlled reopen; it never
continues authenticating against potentially stale permissions.

JWT/certificate modes retain their existing protocol and policy semantics. Provider mode extends
wire version 3 with explicit mode/message values; old peers reject these rather than downgrading.
The new server-authenticated account receipt is not a bearer credential. This change adds native
accounts to the public TCP host, encoded client and typed repository. Other integrations that
explicitly require JWT must retain that mode until they support provider identities; this does not
silently change their offline-access or synchronization contracts.
